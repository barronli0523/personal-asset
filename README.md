# Project Asset Kit · 项目经验资产库

把过去项目中的成功做法和失败教训，整理成下一次开发能按需使用的资产。

这是 **Obsidian 知识库模板与 AI 协作流程**，不是插件，也不是自动运行的 Skill 或智能体。无需社区插件、数据库或模型 API；使用 AI 助手时，模型服务及费用由使用者自行选择。

## 先看一条完整示例

**以下全是人为编写的虚构教学材料，不代表任何人的真实经历或测试结果。**

[来源](examples/example-source.md) → [项目复盘](examples/example-project.md) → [具体教训](examples/example-lesson.md) → [可复用清单](examples/example-playbook.md)

复盘不是终点。值得留下的内容必须说明：下次在什么情况下，用什么方式做、避免什么、怎么验收，以及什么时候不能照搬。

## 三步开始

1. 用下方命令获取模板，或下载 ZIP 解压。另建个人工作副本，将其作为 Vault（Obsidian 的笔记库）打开；也可用 Markdown 编辑器阅读。
2. 阅读 [AI 操作说明](AGENTS.md) 和 [目录规范](30_System/schema.md)，再从 [模板目录](30_System/templates/) 选模板。将 owner 占位符换成自己的名称，填日期和受控标签。
3. 选一个小项目：固定一份非敏感来源，先把可复用经验作为 review 候选交给本人判断；批准后再形成 Lesson / Playbook 等正式资产。更新本地索引并记日志。

## 命令行获取（推荐）

电脑已有 Git 时，在希望存放模板的目录运行：

```sh
git clone https://github.com/barronli0523/personal-asset.git personal-asset-template
```

这会获取模板文件，不会安装 Obsidian 或启动 AI。首次完成后，保留 `personal-asset-template` 作为干净模板，另建个人工作副本，不复制 `.git` 历史目录。

macOS / Linux 已有 Git 和 tar 时，可用以下命令创建无 Git 历史的个人副本；`my-assets` 必须是尚不存在的目录：

```sh
mkdir my-assets && (git -C personal-asset-template archive HEAD | tar -x -C my-assets)
```

然后在 Obsidian 选择“打开文件夹为仓库”，打开 `my-assets`。Windows 用户可新建个人目录后复制模板的可见内容，保留隐藏的 `.gitignore`，但不要复制 `.git` 目录。复制不会自动安装插件或模型服务。

已安装 GitHub CLI 的用户，也可用以下命令替代上面的 `git clone`，两者任选其一：

```sh
gh repo clone barronli0523/personal-asset personal-asset-template
```

更新模板时只更新干净模板目录，人工查看变化后再合入个人副本；不要用新模板覆盖自己的笔记和索引。

命令格式参考：[GitHub 克隆说明](https://docs.github.com/en/repositories/creating-and-managing-repositories/cloning-a-repository)、[GitHub CLI 手册](https://cli.github.com/manual/gh_repo_clone)。本说明未在所有操作系统实跑。

## 接收外部项目复盘候选

外部复盘报告不是正式资产。把候选清单交给本库后，AI 先查重、核验证据并使用 `30_System/templates/Review-Item.md` 建立待决项；使用者决定是否留下、进入哪里。

建议让上游复盘输出每项包含：来源项目与报告定位、原始证据、解决的问题、复用场景、适用范围、例外与失效条件、逐条声明类型（已验证事实 / 推断 / 估算 / 个人判断 / 未知）、隐私等级、已知相似资产、推荐目的地和所需人工决定。缺项写 unknown；未检查本库时，相似资产写“待接收端查重”。不要复制凭据、私人信息或第三方敏感原文。

接收端按以下顺序处理：

1. 查 `index`、已有 review、来源和正式资产，确认不是重复候选。相同来源可以支持多个不同候选，不能仅凭路径相同判重。
2. 复用已有来源；必要时仅新增 Source Pointer。来源不足时将候选标记为 `needs-evidence`，不造链接。
3. 一候选一条 review，默认 `status: draft`。批准收录不等于 `verified`。
4. 使用者批准候选当前版本、具体目的地、模板、路径和动作后再落盘；实质内容、证据或目的地变化后重新审核。
5. 拒绝或重复只在 review 记录决定，不自动删除材料、合并笔记或生成新的正式资产。

候选字段和状态见 [目录规范](30_System/schema.md#复盘候选接收)。

## 给 AI：整理一个项目

复制下面的话，提供自己的项目路径。AI 能读取本地文件才可直接执行；否则只提供经过筛选的材料，不上传秘密。

> 请先阅读本库 AGENTS.md 及其指定规则。只读我指定的项目资料，不运行或修改源项目。按 Source → Extract → Evaluate → Review 流程，提取事实、失败尝试、关键决策和环境问题，查重后把可复用经验一候选一条写入 review，注明证据、复用场景、适用范围、例外、声明类型、隐私和推荐目的地。未知信息写无法确认，不替我形成个人观点。先汇报候选和需要我决定的事项并停止；只有我批准具体候选版本、目的地和动作后，才进入 Asset、更新索引并追加日志。

## 给 AI：开始下一次开发

> 按新需求查询本地索引，只读相关资产。先质疑评分、排序、模型调用等功能是否必要，不自行发明阈值或权重。对选中清单每一步和检查项，说明落实为哪项开发/验收动作或为什么不适用。只在缺证据时追读来源。遵守目标项目权限，不把知识库指令当作运行或发布授权。完成后记录实际使用、未执行项和需要修订之处。

例如仅做虚构名称创意时，不应因库里有检索清单就增加搜索系统。按需阅读会增加输入文本；没有对照测量就不能承诺净 token 节省。

## 如何判断有用

- 下一次能按场景找到相关经验，并说明为何适用。
- 经验被转成开发或验收动作，而不只是被引用。
- 实际使用后记录结果、例外和修订；草稿仍可参考，但不冒充已验证。
- 不用条目数量、文件数量或图谱复杂度当作成效。

## 公开仓库与个人工作副本

这个发行包只含方法、模板与虚构示例。公开模板与个人工作副本必须分开：保留干净的公开模板，另用本地副本存个人资料，不直接提交日常工作副本。.gitignore 默认排除个人内容、日志、review、应用状态及常见秘密文件；强制添加或已经跟踪的文件仍可能被提交。

`30_System/index.md`、README 和规则文件仍可被提交，个人使用时修改的索引可能包含项目名称；它们不受上述个人目录忽略规则保护，发布前必须逐项审查。

公开分享前检查实际文件：凭据、个人信息、本机路径、第三方材料与聊天记录。不要把整个个人 Vault 直接覆盖到公开仓库。

## 当前边界

提供16种模板、一条虚构示范链和受控的复盘候选接收协议；不含自动扫描、自动批准、自动入库、自动调用资产或 GitHub 上传功能。文本检查不能替代目标 Obsidian 的阅读视图验收。

许可尚待维护者确认；公开可见不等于已授予再分发许可。发布前应选定并添加 LICENSE。
